# Resume frames on Continue Watching

The Continue Watching shelf now shows **the frame you stopped on** instead of
the poster. A poster tells you which film it is; the frame tells you where you
are in it, which is the only question that row asks — and it is what makes a
shelf of similar-looking posters scannable.

Tracker: #513.

## How it works

`ResumeFrames` pulls a single JPEG out of the file at the saved position. `-ss`
goes **before** `-i`, so ffmpeg seeks to the nearest keyframe rather than
decoding from the start: measured at **134ms for a 26KB 640px image** on a real
file in this library.

Positions round down to ten seconds before becoming a filename, so scrubbing
about reuses a frame instead of writing a near-identical JPEG per progress
tick. The profile is part of the path, because two people are at different
points in the same episode and showing one person's frame to the other would be
both wrong and a small privacy leak.

The API sends the frames beside the items as `resume_frames`, keyed by item id,
rather than replacing `artwork`. A client that has not been updated still
renders posters, and an updated one falls back to the poster whenever a frame
is absent — which is a normal outcome, not an error: nothing watched far enough
in, the file on another machine, ffmpeg missing, a format that resists seeking.

## Three bugs found while building it

**The same film appeared twice.** Selecting the position alongside the item
defeated the `distinct()` that had been keeping one row per item, so a film with
two play sessions became two cards — seen in the real library at 240s and 111s.

**`MAX(position_seconds)` shows the wrong frame.** The furthest point ever
reached is not where the viewer is. Restarting something abandoned near the end
puts the latest session at a couple of minutes while the maximum is still near
the end, so the card would have shown a frame from the finale of a film just
restarted — a spoiler generated by the home page.

**A positionless play row dropped an item off the shelf entirely.** Replacing
`distinct()` with `GROUP BY` fixed the duplicates but left the sort column an
arbitrary joined row. `position_seconds` is nullable and genuinely null in this
library — item 7196 has eleven play rows and the three most recent carry no
position at all — and such an item vanished from Continue Watching.

The shelf query now joins nothing: a `whereHas` filter with the position and the
sort time as correlated subqueries. One row per item by construction, and both
values come from the session the viewer actually left off in.

## Cost, and reclaiming

A cold shelf would have run one synchronous ffmpeg call per card inside a single
web request. Frames already on disk are now served for the price of a
`file_exists` each, and a request extracts at most **four** new ones; the rest
come back without a frame and the client shows the poster. A shelf therefore
fills in over a couple of visits instead of stalling once.

Nothing previously reclaimed the images, so the cache grew by one JPEG per item
per ten seconds watched and never shrank. Finishing an item now drops its
frames, scoped to the profile that finished it — other people sharing the server
may be part-way through the same episode. Cleanup failures are logged and
swallowed: this is housekeeping behind a progress write the player is waiting
on, and a full disk must not turn "you finished the film" into an error.

## Still to do

- **No client renders the frames yet.** The API carries them; iOS, desktop and
  web still draw the poster. That is the next piece of #513.
- **Extraction itself is untested**, deliberately: it needs ffmpeg and a real
  video, and a test that shells out to ffmpeg tests the machine. Everything
  deciding *whether* and *where*, plus the reclaim path, is covered — 14 tests
  in `ResumeFramesTest`, and each was confirmed to fail against the specific
  bug it guards.
- **Frames for items deleted from the library are not reclaimed**, only those
  for items someone finishes. A sweep keyed on item removal is worth adding.
