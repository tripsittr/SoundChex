# 270 — Know what each file is, and what is wrong with it

**Merged** 2026-10-06 · **Issues** #467

Two gaps closed. **No video technical data was stored anywhere** — resolution,
HDR, codecs, channels, languages and bitrate all absent — which is why
keep-best for video compared file *sizes*, letting a bloated 1080p rip beat a
tight 4K remux. And **nothing checked quality at all**: a truncated file, a CAM
rip and a file with no audio stream all imported as healthy, and the owner
found out when they pressed play.

## What changed

### `media_probes` — what ffprobe says a file contains

Container, duration, bitrate, size, video codec, resolution, frame rate, HDR
format, bit depth, every audio stream (codec, channels, layout, language,
bitrate, sample rate, depth) and every subtitle stream — plus the raw ffprobe
output, so a question nobody has asked yet is answerable from stored data
rather than by re-probing the library.

One probe per file, replaced when re-run: a probe measures the bytes as they
are *now*, and after a remux the old numbers describe a file that no longer
exists.

Two details that matter and are easy to get wrong:

- **Cover art is a video stream** by `codec_type`, so a track with an embedded
  sleeve would read as a 300×300 film. `attached_pic` says which, and
  `ContainerProbe` had already learned this.
- **HDR is read from transfer characteristics and side data**, not guessed from
  bit depth — a 10-bit SDR file is common, so depth alone would call half a
  library HDR. Dolby Vision takes precedence because a DV file usually carries
  an HDR10 base layer too.

### `quality_findings` — six cheap checks

| check | severity | why |
|---|---|---|
| `no_video_stream` | **bad** | a film with no picture is audio misfiled, or a broken download |
| `no_audio_stream` | **bad** | nothing to hear |
| `truncated` | **bad** | shorter than its runtime — plays perfectly until it stops |
| `cam_source` | **bad** | the filename says it was filmed off a cinema screen |
| `low_bitrate` | warn | low for the resolution |
| `fake_lossless_container` | warn | too small to be lossless at that sample rate |

Only `bad` parks an item. A library full of blocked files nobody asked about is
how a quality check gets switched off.

`truncated` is the most useful of them: a download that stopped early plays
fine up to the point it stops, so nothing else notices. 5% tolerance, because a
container's duration and a provider's runtime legitimately disagree a little.

**CAM detection splits on word boundaries**, or `ts` matches *Ghostbusters* and
half a library becomes a telesync. Verified: `Ghostbusters.2016.1080p`,
`Transformers.1080p` and `Cats.2019.BluRay` stay clean while `HDCAM` and a bare
`TS` are flagged.

A finding is **cleared** when the file no longer has that problem. A stale
finding is worse than none — it sends somebody looking for something that is
gone.

### The two placeholder stages do their work now

`ProbeStage` and `CheckStage` were pass-throughs when the pipeline landed
(#465). A book is skipped rather than flagged — an EPUB carries no streams, so
ffprobe refusing it is the expected answer.

`CheckStage` names what it found: *"no audio stream (0 streams vs at least one
audio stream)"*, rather than "quality problem", which tells a person nothing.

### `library:probe` for the existing library

Local work only — no network, so no rate limit. `--type`, `--limit`,
`--reprobe`, `--skip-checks`. It distinguishes **"no file on this machine"**
from **"could not be read"** from **"a book carries no streams"**, because
collapsing those into one number is how a library of books reads as a library
of broken files.

## Worth knowing

- **No backfill has run on the Mac**, because the library's files are not on
  this machine — `library:probe --limit=5` measured 0, found 2 with no file and
  3 books. a5 should run it where the media is.
- The expensive checks are **not** here: decoding the whole file for errors,
  and reading the spectrum to catch a lossy file in a lossless container. Those
  belong in a background job that may finish after the item is published,
  because a good file should not wait on them.
- The tests use **real media generated by ffmpeg**, not fixtures — a probe that
  reads a fake proves only that the parser reads the fake. They skip when
  ffprobe is unavailable.
- `php -l` caught an ambiguous ternary (`a ? b : c ?: d`) that PHP refuses to
  parse. Worth running it before anything else, every time.
