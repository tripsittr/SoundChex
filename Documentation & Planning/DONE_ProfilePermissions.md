# Profile Permissions & PINs

Move permissions from the account to the profile, and make that a real
boundary rather than a suggestion.

## Why

A household shares one account. Today every person on it has identical rights,
because permission lives on the `User`. The uploader role was a workaround —
it granted panel access to a whole account when what was wanted was "Syd can
add files, the kids cannot".

Profiles already carry taste and position. Carrying capability too is the
natural extension.

## The problem this has to solve first

**Profiles have no password.** `CurrentProfile::switchTo()` checks only that
the profile belongs to the signed-in account; switching is one click from a
menu, exactly as commercial services do it.

Per-profile permissions on top of that would be decorative: a kid switches to
the "Dad" profile and inherits Dad's rights. The permission would be a label,
not a boundary.

So a PIN comes first. **Only profiles that can do more than the baseline need
one** — a kids profile with fewer rights than everyone else has nothing worth
protecting, and asking a child for a PIN to watch cartoons is friction with no
purpose.

## The model

**One household account. Its first profile is the owner.** Everyone in the
house signs into the same login and picks their profile; the owner creates the
others and decides what each may do.

So capability lives entirely on the profile:

| | Role |
|---|---|
| **Account** | Who may reach this server at all — one login, shared |
| **Owner profile** | Full rights. Created with the account, cannot be demoted |
| **Other profiles** | Exactly what the owner grants, nothing by default |

The account is deliberately *not* a ceiling. It grants everything, and the
profile subdivides it — otherwise the owner could not give a household member
a right the shared login would then have to hold anyway.

This puts the whole weight on the PIN: since every login reaches the panel,
the profile is the only thing standing between a household member and the
owner's rights. A profile with elevated permissions must have one.

## Scope

**In:**

- Real per-resource permissions, generated by `shield:generate`, replacing the
  hardcoded role check in `RestrictsToAdmins`
- Permissions attachable to a profile, not only a role
- Roles kept as presets — "Uploader" as a starting bundle, then adjusted per
  profile
- A PIN on any profile holding permissions beyond the account baseline
- PIN required to switch into such a profile; required to change its own PIN
- Rate limiting on PIN attempts

**Out:**

- A PIN on unprivileged profiles. Nothing to protect, and it makes the picker
  worse for the people who use it most.
- PIN recovery by email. This is a home server with no mail configured; an
  admin resets a forgotten PIN from `/admin/profiles`.
- Per-item permissions ("Syd may edit this album but not that one"). Per
  resource is the useful granularity.

## Approach

1. `shield:generate` for real permissions across every resource. This is also
   the fix for a live gap: the media resources currently have **no permissions
   at all**, so only the panel gate stands between any panel user and user
   management.
2. `profile_permissions` pivot, and a `Profile::can()` that consults the
   profile alone — the owner profile short-circuits to true, everything else
   is explicit grants.
3. `pin_hash` on profiles, hashed like a password, never stored in the clear.
4. Switching into a profile with a PIN prompts for it; failures throttled.
5. `RestrictsToAdmins` asks the current profile rather than testing a role.

## The risk worth naming

**A permission check that reads the wrong subject fails open.** There are now
two subjects — account and profile — and code that asks the account when it
means the profile will grant more than intended.

So the check goes through one method, `Profile::can()`, which requires *both*
to allow. No call site decides on its own.

## Verification

- A profile with `Delete:Music` can delete; one without gets 403 by direct URL.
- The owner profile keeps full rights and cannot be locked out.
- A member profile has nothing until granted, and gets 403 by direct URL.
- Switching into a PIN-protected profile without the PIN fails, and the wrong
  PIN is throttled.
- A profile with no elevated permissions still switches in one click.
- An admin can reset a forgotten PIN.
- Existing behaviour is unchanged for an account with one profile.

## Outcome

Built and verified.

**The premise changed mid-build.** The plan had the account acting as a ceiling
over the profile, which is wrong for a shared household login: everyone signing
in would need to hold every right the owner has, defeating the point.
Capability now lives entirely on the profile, and the owner short-circuits so a
household can never be left with nobody able to administer it.

Also fixed a live gap found on the way in: **the media resources had no
permissions at all**. Shield had only ever generated them for Role and User, so
the panel gate was the only thing between any signed-in account and user
management. There are 68 permissions now, covering every resource and settings
page.

`RestrictsToAdmins` derives the permission from the class name, so a new
resource is gated by default rather than by remembering to add one. The `Page`
suffix is stripped — `LibrarySettingsPage` would otherwise ask for a permission
that does not exist and fail closed.

Verified: an owner reaches everything; a member profile is **403 on every
resource by direct URL** until granted, then reaches exactly what was granted
and nothing else. A PIN-protected profile refuses an empty or wrong PIN, locks
after five attempts, and refuses even the correct PIN while locked.
Unprivileged profiles still switch in one tap. Tests 24/24.

## Deferred

PIN recovery by email — no mail is configured on a home server, so an owner
resets a forgotten PIN from `/admin/profiles`. Per-item permissions are not
planned; per resource is the useful granularity.
